模块架构与文件清单

沿用"原生 API → 服务 → 模型 → UI"四层结构，与规划阶段的模块划分一脉相承。数据流为一条单向流水线。

数据流：GDI 捕获（ScreenCapturer）→ 鼠标效果叠加（MouseEffectRenderer）→ 送入 FFmpeg stdin（VideoEncoder）→ 落盘 MP4。RecorderEngine 负责状态机与流水线编排，UI 通过事件获取状态与进度。
层文件职责
Native 原生层NativeMethods.csGDI 捕获、光标位置、磁盘空间 P/Invoke
ScreenCapturer.cs可复用 GDI 捕获器（性能关键）
MouseHook.cs全局低级鼠标钩子，捕获点击事件
Services 服务层RecorderEngine.cs核心状态机 + CFR 捕获循环 + 流水线编排
VideoEncoder.csFFmpeg 进程与 stdin 管道编码
MouseEffectRenderer.cs三项鼠标效果的帧字节级渲染
Models 模型层RecorderSettings.cs全部可配置参数
RecorderState.cs状态枚举（Idle/Recording/Paused/Saving）
Views 界面层MainWindow.xaml(.cs)参数配置、启动录制、历史文件
FloatingControl.xaml(.cs)透明置顶可拖动控制条
PlaybackWindow.xaml(.cs)基础回放播放器

4.2 性能定位（spike/PerfProbe，120 帧采样）

环节耗时理论帧率上限结论
一次性 GDI 捕获26.59 ms/帧37.6 fps逐帧重建资源，开销大
复用式 GDI 捕获21.14 ms/帧47.3 fps资源复用提升约 20%（已采用）
仅 BitBlt（无 GetDIBits）13.62 ms/帧73.4 fpsGetDIBits 转换约占 7.5 ms
鼠标效果渲染0.01 ms/帧—开销可忽略，非瓶颈
性能真相：本机瓶颈是 GDI BitBlt + GetDIBits 捕获本身（8MB/帧像素拷贝），原生捕获率约 22fps。MVP 通过 CFR 补帧输出稳定 30fps，视频时长准确，但补帧意味着部分帧是重复画面——快速移动场景的流畅度不及真实 30fps 采集。这是 GDI 方案的固有局限，非代码缺陷。
5

发现并修复的真实缺陷

开发过程中通过真实运行暴露了 3 个缺陷，均已定位根因并修复，不是估算或假设。

#现象根因修复
1进程启动即抛异常，无法录制VideoEncoder 设置了 StandardOutputEncoding 却未重定向 stdout，.NET 拒绝启动进程移除该设置（stdout 本未使用）；GUI/控制台均会触发，属必修缺陷
2捕获耗时偏高（26.6ms/帧）每帧重建 DC、兼容位图、分配缓冲并释放新增可复用 ScreenCapturer，资源构造一次循环复用，降至 21.1ms/帧
3视频被加速：录 6 秒成 4.4 秒实际约 22fps 捕获，却按 30fps 写入 FFmpeg，时间戳按 30fps 计算导致播放加速改为 CFR 逻辑时钟补帧：帧数=时长×30，捕获不足时重复上一帧；修复后录 6 秒成 6.5 秒，时长准确
缺陷 3 是本次最重要的发现。它不会导致编译失败或崩溃，只会让"回放速度变快"——若不做真实录放对照极易漏过。已通过实测时长比对确认修复有效。

遗留风险与后续选项

项目性质说明与建议
原生捕获率约 22fps已知限制不影响 MVP 交付（CFR 保证时长与可播放性）；快速移动场景流畅度受限
Graphics Capture 未启用可选优化本机缺 Windows SDK 未能验证；安装后可能突破 GDI 帧率瓶颈，但需 D3D11 互操作，改动较大
NVENC 硬编码未启用可选优化驱动 31.0.15.2727 仅支持 NVENC API 12.0（FFmpeg 需 13.1）；升级驱动到 610+ 后可启用，降低 CPU 占用
GUI 交互未做人工试录待人工验证已验证程序可启动、引擎端到端可用；按钮点击的实际手感与悬浮条拖动建议本人实测一轮
阶段 2 功能后续范围音频采集与混录、窗口/区域录制、按键提示，按规划在阶段 2 实现
