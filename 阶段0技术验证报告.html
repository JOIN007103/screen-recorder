选型结论与技术变更

基于实测数据，固化阶段 1 的三项技术选型。其中编码方案发生变更，需同步调整 WBS 与模块设计。

选型项规划推荐实测结论（最终）依据
屏幕捕获Windows Graphics CaptureGDI BitBlt（已验证）GDI 实测 30.2fps/CPU 0.4% 达标；Graphics Capture 因缺 Windows SDK 未能编译验证，列为可选增强
视频编码Media Foundation Sink WriterFFmpeg libx264（变更）MF 缺 msmpeg2venc.dll 无法编码 H.264；FFmpeg 实测编码正确、解码完整
编码调用方式进程内 COM外部进程 + 标准输入管道FFmpeg 以子进程运行，C# 通过 stdin 送入 bgr24 原始帧
UI 框架WPFWPF（未变更，待阶段 1 验证）本阶段未涉及 UI，保持规划结论

编码方案变更详情（重要）

Media Foundation 路径的失败经过完整诊断，确认为环境组件缺失而非配置错误：

诊断步骤结果
MFStartup / 创建 SinkWriter / 设置属性全部成功（0x00000000）
AddStream(H.264)失败 0xC00D36E6（MF_E_INVALIDMEDIATYPE）
加 Profile 属性 / 换 NV12 输入 / 缩小到 640×360 / 启用硬件变换均失败，错误一致
检查 msmpeg2venc.dll（MF 的 H.264 编码器）缺失 — 根因确认
FFmpeg libx264 替代编码成功 — 输出参数正确、解码完整
对 WBS 的影响：WP2.1「H.264 编码集成」的实现方式由进程内 COM 改为 FFmpeg 外部进程管理 + 管道数据流，需增加"FFmpeg 进程生命周期管理"与"原始帧传输"两项子任务。整体工时估算影响较小（FFmpeg 集成成熟），但阶段 1 模块设计需据此调整。详细差异见阶段 1 设计文档（后续产出）。

待办、风险与 Go/No-Go

4.1 可选增强待办（不阻塞阶段 1）

待办优先级说明
升级 NVIDIA 驱动以启用 NVENC 硬编码中当前驱动仅支持 NVENC API 12.0，FFmpeg 要求 13.1（需驱动 610+）。升级后可用 h264_nvenc，进一步降低 CPU 占用
安装 Windows SDK 补验 Graphics Capture低GDI 已达标；Graphics Capture 支持窗口捕获与更好的多屏体验，可在阶段 2/3 需要时再验证

4.2 遗留风险

风险等级应对
FFmpeg 外部进程分发体积与依赖中绿色版需携带 ffmpeg.exe；体积约数十 MB，可接受；或用精简构建
管道传输原始帧的带宽压力低1080p/30fps bgr24 约 180MB/s，实测 CPU 仅 1.2%，当前无瓶颈
NVENC 硬编码不可用（驱动旧）低libx264 软编码已达标，硬编码为可选优化

4.3 Go/No-Go 决策

最终结论：阶段 0 验证通过，建议进入阶段 1（MVP）开发。进入前需老大确认一项变更——编码方案由 Media Foundation 改为 FFmpeg libx264（已在报告中给出充分依据）。确认后即按调整后的模块设计推进阶段 1。
